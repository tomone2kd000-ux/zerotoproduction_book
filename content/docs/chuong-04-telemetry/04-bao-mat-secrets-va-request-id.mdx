# Bảo Mật Secrets, Request ID & Tối Ưu Hóa Telemetry

Trong các bài học trước, chúng ta đã xây dựng thành công pipeline thu thập dữ liệu giám sát với `tracing`, `tracing-subscriber` và định dạng JSON Bunyan. Bây giờ là lúc một Senior Developer nhìn lại toàn bộ kiến trúc để:
1. Chuẩn hóa và đóng gói mã nguồn khởi tạo telemetry;
2. Tích hợp telemetry vào bộ kiểm thử tích hợp (integration tests);
3. Dùng macro `#[tracing::instrument]` để giữ cho logic nghiệp vụ trong sáng;
4. Ngăn chặn triệt để nguy cơ rò rỉ mật khẩu và dữ liệu nhạy cảm ra log với `secrecy`;
5. Đồng bộ `request_id` xuyên suốt từ middleware tới tầng cơ sở dữ liệu.

## 4.5.10. Tối Ưu Hóa Khởi Tạo Telemetry (Module `telemetry.rs`)

Hiện tại, hàm `main` của chúng ta đang chứa quá nhiều chi tiết kỹ thuật về việc lắp ghép các tầng subscriber. Hãy trừu tượng hóa logic này bằng cách tạo ra hai hàm:
- `get_subscriber`: Lắp ráp các layer (`EnvFilter`, `JsonStorageLayer`, `BunyanFormattingLayer`) thành một subscriber hoàn chỉnh.
- `init_subscriber`: Đăng ký subscriber đó làm mặc định toàn cục cho ứng dụng.

Tạo file mới `src/telemetry.rs`:

```rust
//! src/telemetry.rs
use tracing::subscriber::set_global_default;
use tracing::Subscriber;
use tracing_bunyan_formatter::{BunyanFormattingLayer, JsonStorageLayer};
use tracing_log::LogTracer;
use tracing_subscriber::fmt::MakeWriter;
use tracing_subscriber::{layer::SubscriberExt, EnvFilter, Registry};

/// Kết hợp nhiều layer thành một `tracing` Subscriber.
///
/// Sử dụng `impl Subscriber + Send + Sync` làm kiểu trả về để che giấu
/// kiểu phức tạp bên dưới, đồng thời đảm bảo subscriber có thể truyền an toàn giữa các luồng.
pub fn get_subscriber<Sink>(
    name: String,
    env_filter: String,
    sink: Sink,
) -> impl Subscriber + Send + Sync
where
    // Higher-Ranked Trait Bound (HRTB): Sink phải hiện thực MakeWriter cho mọi lifetime 'a
    Sink: for<'a> MakeWriter<'a> + Send + Sync + 'static,
{
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(env_filter));
    let formatting_layer = BunyanFormattingLayer::new(name, sink);
    Registry::default()
        .with(env_filter)
        .with(JsonStorageLayer)
        .with(formatting_layer)
}

/// Đăng ký subscriber làm mặc định toàn cục để xử lý dữ liệu spans.
/// Hàm này chỉ được gọi đúng 1 lần duy nhất trong suốt vòng đời tiến trình.
pub fn init_subscriber(subscriber: impl Subscriber + Send + Sync) {
    LogTracer::init().expect("Không thể thiết lập LogTracer.");
    set_global_default(subscriber).expect("Không thể thiết lập global subscriber.");
}
```

Khai báo module mới trong `src/lib.rs`:

```rust
//! src/lib.rs
pub mod configuration;
pub mod routes;
pub mod startup;
pub mod telemetry;
```

Bây giờ file `src/main.rs` trở nên vô cùng ngắn gọn và tường minh:

```rust
//! src/main.rs
use sqlx::PgPool;
use std::net::TcpListener;
use zero2prod::configuration::get_configuration;
use zero2prod::startup::run;
use zero2prod::telemetry::{get_subscriber, init_subscriber};
use secrecy::ExposeSecret;

#[tokio::main]
async fn main() -> Result<(), std::io::Error> {
    let subscriber = get_subscriber("zero2prod".into(), "info".into(), std::io::stdout);
    init_subscriber(subscriber);

    let configuration = get_configuration().expect("Không thể đọc cấu hình.");
    let connection_pool = PgPool::connect(&configuration.database.connection_string().expose_secret())
        .await
        .expect("Không thể kết nối cơ sở dữ liệu PostgreSQL.");

    let address = format!("127.0.0.1:{}", configuration.application_port);
    let listener = TcpListener::bind(address)?;
    run(listener, connection_pool)?.await
}
```

## 4.5.11. Telemetry Cho Bộ Kiểm Thử Tích Hợp (Integration Tests)

Mọi năng lực vận hành trong ứng dụng chính cần phải được phản ánh tương ứng trong bộ kiểm thử tích hợp. Khi một test case bị lỗi, chính các bản ghi structured log sẽ giúp ta chẩn đoán nguyên nhân ngay lập tức mà không cần gắn debugger.

Hãy mở `tests/health_check.rs`. Khi gắn `init_subscriber` vào hàm `spawn_app`, nếu chạy `cargo test`, ta sẽ gặp ngay lỗi hoảng loạn (panic):

```text
thread 'subscribe_returns_a_400_when_data_is_missing' panicked at 
'Failed to set logger: SetLoggerError(())'
```

**Nguyên nhân**: Cargo chạy các bài test song song trên nhiều luồng. `init_subscriber` được gọi nhiều lần, nhưng logger toàn cục của hệ thống chỉ cho phép đăng ký đúng **một lần duy nhất**.

### Giải Pháp 1: Đảm Bảo Khởi Tạo Đơn Lần Với `once_cell`

Thêm `once_cell` vào `[dev-dependencies]` trong `Cargo.toml`:

```toml
#! Cargo.toml
[dev-dependencies]
once_cell = "1"
```

Sử dụng `once_cell::sync::Lazy` trong `tests/health_check.rs`:

```rust
//! tests/health_check.rs
use once_cell::sync::Lazy;
use zero2prod::telemetry::{get_subscriber, init_subscriber};

// Đảm bảo pipeline Tracing chỉ được khởi tạo đúng 1 lần duy nhất
static TRACING: Lazy<()> = Lazy::new(|| {
    let default_filter_level = "info".to_string();
    let subscriber_name = "test".to_string();

    // Nếu biến môi trường TEST_LOG được gán, xuất log ra stdout.
    // Ngược lại, đẩy log vào std::io::sink (vứt bỏ hoàn toàn) để tránh làm bẩn màn hình test.
    if std::env::var("TEST_LOG").is_ok() {
        let subscriber = get_subscriber(subscriber_name, default_filter_level, std::io::stdout);
        init_subscriber(subscriber);
    } else {
        let subscriber = get_subscriber(subscriber_name, default_filter_level, std::io::sink);
        init_subscriber(subscriber);
    }
});

async fn spawn_app() -> TestApp {
    // Ép khối khởi tạo TRACING thực thi trong lần gọi đầu tiên
    Lazy::force(&TRACING);

    // [...] Phần còn lại của spawn_app
}
```

Bây giờ:
- Khi chạy `cargo test`: Màn hình hoàn toàn sạch sẽ, không bị log làm nhiễu.
- Khi cần debug một test case cụ thể, bạn chỉ cần bật cờ `TEST_LOG=true`:

```bash
TEST_LOG=true cargo test subscribe_returns_a_200 | bunyan
```

Toàn bộ cây Span và Event JSON sẽ được hiển thị định dạng màu sắc đẹp mắt qua công cụ dòng lệnh `bunyan`!

## 4.5.12. Tinh Gọn Mã Nguồn Với Macro `#[tracing::instrument]`

Nhìn vào hàm `subscribe`, chúng ta nhận thấy mã logging thủ công đang làm phân tán logic chính. Chúng ta muốn bọc toàn bộ hàm `subscribe` vào một Span một cách tự nhiên.

Crate `tracing` cung cấp procedural macro cực mạnh: `#[tracing::instrument]`.

```rust
//! src/routes/subscriptions.rs
use actix_web::{web, HttpResponse};
use chrono::Utc;
use sqlx::PgPool;
use uuid::Uuid;

#[derive(serde::Deserialize)]
pub struct FormData {
    pub email: String,
    pub name: String,
}

#[tracing::instrument(
    name = "Adding a new subscriber",
    skip(form, pool),
    fields(
        subscriber_email = %form.email,
        subscriber_name = %form.name
    )
)]
pub async fn subscribe(
    form: web::Form<FormData>,
    pool: web::Data<PgPool>,
) -> HttpResponse {
    match insert_subscriber(&pool, &form).await {
        Ok(_) => HttpResponse::Ok().finish(),
        Err(_) => HttpResponse::InternalServerError().finish(),
    }
}

#[tracing::instrument(
    name = "Saving new subscriber details in the database",
    skip(pool, form)
)]
pub async fn insert_subscriber(
    pool: &PgPool,
    form: &FormData,
) -> Result<(), sqlx::Error> {
    sqlx::query!(
        r#"
        INSERT INTO subscriptions (id, email, name, subscribed_at)
        VALUES ($1, $2, $3, $4)
        "#,
        Uuid::new_v4(),
        form.email,
        form.name,
        Utc::now()
    )
    .execute(pool)
    .await
    .map_err(|e| {
        tracing::error!("Thực thi truy vấn thất bại: {:?}", e);
        e
    })?;
    Ok(())
}
```

### Lợi Ích Của `#[tracing::instrument]`
1. **Phân tách trách nhiệm hoàn hảo**: Cấu hình telemetry nằm ở phần attribute trang trí cho hàm; thân hàm chỉ tập trung vào luồng điều phối nghiệp vụ thuần túy.
2. **Hỗ trợ async nguyên bản**: Macro tự động sử dụng `Instrument::instrument` dưới nắp capo để bảo đảm việc enter/exit Span khớp chính xác với từng lần Tokio poll future.
3. **Phân tầng kiến trúc sạch sẽ**: Tách hàm con `insert_subscriber` giúp tách biệt tầng Web Framework (`web::Data`, `web::Form`) khỏi tầng tương tác CSDL thuần túy (`&PgPool`, `&FormData`).

## 4.5.13. Bảo Vệ Dữ Liệu Nhạy Cảm (Secrets) Với Crate `secrecy`

Macro `#[tracing::instrument]` mặc định sẽ log toàn bộ đối số truyền vào hàm. Đây là cơ chế **opt-out** (mặc định log, muốn bỏ phải ghi `skip`).

Trong thực tế phát triển phần mềm, nếu một lập trình viên thêm một tham số như `password` hay `credit_card_number` vào hàm mà quên không khai báo `skip(...)`, bí mật đó sẽ lập tức bị in trần (plaintext) ra hệ thống log tập trung — dẫn đến một thảm họa bảo mật nghiêm trọng (như sự cố Facebook từng vô tình lưu trữ hàng trăm triệu mật khẩu người dùng ở dạng plaintext vào hệ thống log nội bộ).

Để ngăn chặn tận gốc rủi ro này từ cấp độ hệ thống kiểu (type system), chúng ta sử dụng crate [`secrecy`](https://docs.rs/secrecy):

```toml
#! Cargo.toml
[dependencies]
secrecy = { version = "0.8", features = ["serde"] }
```

Struct `Secret<S>` bao bọc lấy giá trị nhạy cảm với các đặc tính bảo vệ then chốt:
- **Không triển khai trait `Display`**: Tránh việc vô tình format vào chuỗi bằng `{}`.
- **Ẩn giấu trait `Debug`**: Khi gọi `println!("{:?}", secret)`, output in ra luôn là `Secret([REDACTED String])`.
- **Triển khai trait `Zeroize`**: Tự động ghi đè vùng nhớ chứa dữ liệu nhạy cảm bằng số 0 khi biến bị hủy (dropped) khỏi bộ nhớ RAM.

Hãy áp dụng `Secret<String>` cho mật khẩu cơ sở dữ liệu trong `src/configuration.rs`:

```rust
//! src/configuration.rs
use secrecy::{ExposeSecret, Secret};

#[derive(serde::Deserialize)]
pub struct DatabaseSettings {
    pub username: String,
    pub password: Secret<String>, // Bọc mật khẩu trong Secret
    pub port: u16,
    pub host: String,
    pub database_name: String,
}

impl DatabaseSettings {
    pub fn connection_string(&self) -> Secret<String> {
        Secret::new(format!(
            "postgres://{}:{}@{}:{}/{}",
            self.username,
            self.password.expose_secret(),
            self.host,
            self.port,
            self.database_name
        ))
    }

    pub fn connection_string_without_db(&self) -> Secret<String> {
        Secret::new(format!(
            "postgres://{}:{}@{}:{}",
            self.username,
            self.password.expose_secret(),
            self.host,
            self.port
        ))
    }
}
```

Bất cứ khi nào cần truy cập giá trị mật khẩu thô để kết nối CSDL, Rust bắt buộc chúng ta phải gọi tường minh phương thức `.expose_secret()`:

```rust
let connection_pool = PgPool::connect(&configuration.database.connection_string().expose_secret())
    .await
    .expect("Không thể kết nối cơ sở dữ liệu.");
```

Trình biên dịch của Rust giờ đây trở thành người gác cổng đáng tin cậy: **Không một bí mật nào có thể vô tình rò rỉ ra log nếu không có sự cho phép có chủ đích bằng phương thức `expose_secret()`!**

## 4.5.14. Tích Hợp Request ID Xuyên Suốt Với `tracing-actix-web`

Nhiệm vụ cuối cùng của chúng ta là giải quyết bài toán: **Làm sao để dòng log HTTP Response (mã 200/400/500 do framework xuất ra) cũng mang đúng `request_id` của request đó?**

Thay vì tự viết middleware phức tạp, chúng ta sử dụng crate [`tracing-actix-web`](https://docs.rs/tracing-actix-web):

```toml
#! Cargo.toml
[dependencies]
tracing-actix-web = "0.7"
```

Crate này cung cấp middleware `TracingLogger` — một sự thay thế hoàn hảo cho `actix_web::middleware::Logger`. Nó tự động:
1. Sinh mã UUID `request_id` cho mỗi request đi vào;
2. Khởi tạo một Root Span bao trùm toàn bộ quá trình xử lý;
3. Gắn thông tin HTTP method, path, client IP và status code vào dữ liệu có cấu trúc.

Cập nhật `src/startup.rs`:

```rust
//! src/startup.rs
use actix_web::dev::Server;
use actix_web::web::Data;
use actix_web::{web, App, HttpServer};
use sqlx::PgPool;
use std::net::TcpListener;
use tracing_actix_web::TracingLogger;
use crate::routes::{health_check, subscribe};

pub fn run(
    listener: TcpListener, 
    db_pool: PgPool
) -> Result<Server, std::io::Error> {
    let db_pool = Data::new(db_pool);
    let server = HttpServer::new(move || {
        App::new()
            // Sử dụng TracingLogger thay cho Logger::default()
            .wrap(TracingLogger::default())
            .route("/health_check", web::get().to(health_check))
            .route("/subscriptions", web::post().to(subscribe))
            .app_data(db_pool.clone())
    })
    .listen(listener)?
    .run();
    Ok(server)
}
```

<Callout type="warn">
  **Đồng bộ Request ID**: Trong hàm `subscribe`, chúng ta hãy **xóa bỏ** dòng `request_id = %Uuid::new_v4()` khỏi macro `#[tracing::instrument]`. `TracingLogger` đã sinh `request_id` ở tầng Root Span, và Span con trong `subscribe` sẽ tự động thừa hưởng chính xác ID này mà không tạo ra sự phân mảnh định danh.
</Callout>

## 4.5.15. Hệ Sinh Thái Tracing Mở Rộng

Pipeline mà chúng ta vừa xây dựng hoàn toàn tương thích với chuẩn **OpenTelemetry** — tiêu chuẩn công nghiệp hiện nay cho việc giám sát hệ thống phân tán:
- **`tracing-opentelemetry`**: Cho phép đẩy toàn bộ dữ liệu trace trực tiếp tới các hệ thống phân tán chuyên sâu như Jaeger, Zipkin, Honeycomb.io hoặc Datadog APM.
- **`tracing-error`**: Bổ sung `SpanTrace` vào các kiểu lỗi nghiệp vụ, cho phép in ra toàn bộ cây phân cấp các Span dẫn tới sự cố khi có lỗi xảy ra.

## 4.6. Tổng Kết Chương 4

Qua Chương 4, chúng ta đã biến một dịch vụ backend đơn sơ từ trạng thái "hoàn toàn mù lòa" trở thành một hệ thống có **Khả năng quan sát cấp độ doanh nghiệp (Enterprise Observability)**:

```text
HTTP Request ──► [TracingLogger] ──(gán request_id)
                       │
                       ▼
                 [subscribe Span] ──(thừa hưởng request_id, email, name)
                       │
                       ▼
            [insert_subscriber Span] ──(thừa hưởng context, đo thời gian truy vấn SQL)
                       │
                       ▼
              Output Bunyan JSON ──► Datadog / ElasticSearch / Console
```

1. **Khả năng quan sát (Observability)** giúp chúng ta chẩn đoán các lỗi không thể lường trước (*unknown unknowns*) ngoài môi trường Production.
2. **Crate `tracing`** thay thế hoàn toàn tư duy logging văn bản cổ điển bằng cấu trúc cây **Span**, quản lý thời lượng và lan truyền ngữ cảnh tự nhiên.
3. **Mô hình Layering** giúp tách biệt pipeline xử lý log thành các tầng lọc (`EnvFilter`), trích xuất (`JsonStorageLayer`), và định dạng (`BunyanFormattingLayer`).
4. **Bảo mật tuyệt đối** với `secrecy::Secret` bảo vệ mật khẩu khỏi rò rỉ vô tình.
5. **Request ID xuyên suốt** với `tracing-actix-web` mang lại khả năng truy vết tức thì mọi request của người dùng từ đầu tới cuối.

Hệ thống của chúng ta hiện đã vững vàng và sẵn sàng ra biển lớn. Trong **Chương 5: Going Live**, chúng ta sẽ chính thức đóng gói ứng dụng bằng Docker và triển khai lên hạ tầng Cloud thực tế!
