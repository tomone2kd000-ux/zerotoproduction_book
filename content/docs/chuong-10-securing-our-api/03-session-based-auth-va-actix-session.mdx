# 10.7 Quản Lý Phiên (Session-based Auth) Với Redis & actix-session

Sau khi người dùng đăng nhập thành công qua form ở trang `/login`, chúng ta không thể bắt họ phải tiếp tục nhập lại username và mật khẩu mỗi khi chuyển sang trang khác. 

Giao thức HTTP là một giao thức **Phi trạng thái (Stateless)**: mỗi request gửi lên máy chủ là một thực thể hoàn toàn độc lập, không hề mang theo ký ức về những gì đã diễn ra trước đó. Để duy trì trạng thái đăng nhập xuyên suốt hành trình lướt web, chúng ta cần tới **Quản lý phiên (Session Management)**.

---

## I. Cơ Chế Xác Thực Dựa Trên Phiên (Session-based Authentication)

Quy trình xác thực dựa trên phiên diễn ra như sau:
1. Người dùng gửi thông tin đăng nhập (`username` & `password`) lên endpoint `POST /login`.
2. Máy chủ xác minh mật khẩu qua Argon2id. Nếu hợp lệ, máy chủ sinh ra một chuỗi định danh ngẫu nhiên tuyệt đối không thể đoán trước (**Session Token / Session ID**) bằng bộ sinh số ngẫu nhiên chuẩn mật mã (CSPRNG).
3. Máy chủ lưu trữ cặp khóa-giá trị: `Session ID -> Thông tin phiên (User ID, thời gian hết hạn)` vào một kho dữ liệu trung tâm (**Session Store**).
4. Máy chủ gửi Session ID về trình duyệt qua header `Set-Cookie`.
5. Trong mọi request tiếp theo (ví dụ `GET /admin/dashboard`), trình duyệt tự động đính kèm cookie chứa Session ID. Máy chủ chỉ việc tra cứu Session ID trong kho lưu trữ để biết danh tính người dùng mà không cần chạm tới mật khẩu nữa.

```text
┌───────────┐                                 ┌────────────┐               ┌─────────────┐
│  Browser  │                                 │ Web Server │               │ Redis Store │
└─────┬─────┘                                 └─────┬──────┘               └──────┬──────┘
      │                                             │                             │
      │ 1. POST /login (username, password)         │                             │
      │────────────────────────────────────────────►│                             │
      │                                             │ 2. Verify Argon2id          │
      │                                             │ 3. Generate Session ID      │
      │                                             │                             │
      │                                             │ 4. SET session_id {user_id} │
      │                                             │────────────────────────────►│
      │                                             │◄────────────────────────────│
      │ 5. HTTP 303 (Set-Cookie: session_id=xyz...) │                             │
      │◄────────────────────────────────────────────│                             │
      │                                             │                             │
      │ 6. GET /admin/dashboard (Cookie: xyz...)    │                             │
      │────────────────────────────────────────────►│                             │
      │                                             │ 7. GET session_id           │
      │                                             │────────────────────────────►│
      │                                             │◄────────────────────────────│
      │ 8. HTTP 200 OK (Welcome admin!)             │    Returns {user_id}        │
      │◄────────────────────────────────────────────│                             │
```

## II. Lựa Chọn Kho Lưu Trữ Phiên (Choosing A Session Store)

Kho lưu trữ phiên phải đáp ứng các yêu cầu: Tạo mới (Create), Đọc (Read), Cập nhật (Update), Xóa (Delete) và đặc biệt là **Hết hạn tự động (TTL / Expiration)**.

Hãy cùng phân tích các ứng viên:

```text
┌─────────────────┬───────────────────────────────────┬───────────────────────────────────┐
│ Giải pháp       │ Ưu điểm                           │ Nhược điểm chí mạng               │
├─────────────────┼───────────────────────────────────┼───────────────────────────────────┤
│ 1. In-Memory    │ Tốc độ truy xuất micro-giây,      │ - Mất sạch phiên khi restart app. │
│    HashMap      │ không cần hạ tầng phụ trợ.        │ - Không scale ngang được nhiều    │
│                 │                                   │   server (thiếu session sharing). │
├─────────────────┼───────────────────────────────────┼───────────────────────────────────┤
│ 2. Client-side  │ Máy chủ không tốn tài nguyên      │ - Giới hạn kích thước Cookie 4KB. │
│    Cookie Store │ lưu trữ (Stateless Server).       │ - Rất khó thu hồi (revoke) phiên  │
│                 │                                   │   tức thời từ phía server.        │
├─────────────────┼───────────────────────────────────┼───────────────────────────────────┤
│ 3. PostgreSQL   │ Bền vững, tận dụng luôn database  │ Không có cơ chế TTL native.       │
│                 │ sẵn có của hệ thống.              │ Phải viết cronjob dọn rác định kỳ,│
│                 │                                   │ gây áp lực IO lên DB chính.       │
├─────────────────┼───────────────────────────────────┼───────────────────────────────────┤
│ 4. REDIS        │ Lưu trên RAM cực nhanh, hỗ trợ TTL│ Cần vận hành thêm một service     │
│    (In-memory   │ tự hủy bản ghi, dễ dàng chia sẻ   │ hạ tầng Redis trong cụm máy chủ.  │
│     K-V Store)  │ giữa hàng chục web nodes.         │ (Hoàn toàn xứng đáng đánh đổi!)   │
└─────────────────┴───────────────────────────────────┴───────────────────────────────────┘
```

**Quyết định kiến trúc**: **Redis** là lựa chọn tiêu chuẩn công nghiệp tối ưu nhất cho bài toán Session Management.

## III. Tích Hợp Redis Và `actix-session`

Chúng ta sử dụng crate chính thức [`actix-session`](https://crates.io/crates/actix-session) với tính năng kết nối Redis:

```toml
#! Cargo.toml
[dependencies]
actix-session = { version = "0.7", features = ["redis-rs-tls-session"] }
```

### Cấu hình SessionMiddleware trong `src/startup.rs`

Để bảo vệ cookie khỏi bị giả mạo hoặc đọc trộm trên đường truyền, `actix-session` yêu cầu một khóa mã hóa bí mật (**Master Secret Key**):

```rust
//! src/startup.rs
use actix_session::storage::RedisSessionStore;
use actix_session::SessionMiddleware;
use actix_web::cookie::Key;

// Khởi tạo Redis Session Store
let redis_store = RedisSessionStore::new(redis_uri.expose_secret()).await?;
let secret_key = Key::from(hmac_secret.expose_secret().as_bytes());

let server = HttpServer::new(move || {
    App::new()
        .wrap(TracingLogger::default())
        // Đăng ký SessionMiddleware bọc ngoài toàn bộ ứng dụng
        .wrap(
            SessionMiddleware::builder(redis_store.clone(), secret_key.clone())
                .cookie_name("zero2prod_session".into())
                .cookie_secure(true) // Chỉ cho phép truyền qua HTTPS
                .cookie_http_only(true) // Cấm truy cập qua JavaScript
                .cookie_same_site(actix_web::cookie::SameSite::Lax)
                .build(),
        )
        // [...]
})
```

## IV. Ghi Nhận Phiên Khi Đăng Nhập & Chống Session Fixation

Khi người dùng nhập đúng thông tin tài khoản tại `POST /login`, chúng ta trích xuất `TypedSession` (một wrapper bọc an toàn quanh `Session` của Actix-web) và lưu `user_id`:

```rust
//! src/routes/login/post.rs
use crate::session_state::TypedSession;

pub async fn login(
    form: web::Form<FormData>,
    pool: web::Data<PgPool>,
    session: TypedSession,
) -> Result<HttpResponse, InternalError<LoginError>> {
    // [...]
    match validate_credentials(credentials, &pool).await {
        Ok(user_id) => {
            // QUAN TRỌNG: Làm mới Session ID để chống tấn công Session Fixation!
            session.renew();
            
            // Ghi user_id vào phiên
            session.insert_user_id(user_id).map_err(e500)?;
            
            Ok(HttpResponse::SeeOther()
                .insert_header((actix_web::http::header::LOCATION, "/admin/dashboard"))
                .finish())
        }
        Err(e) => {
            // [...]
        }
    }
}
```

<Callout type="warn" title="Lỗ hổng Session Fixation Attack">
Nếu bạn giữ nguyên Session ID cũ sau khi người dùng nâng cấp từ trạng thái vô danh (anonymous) sang đã xác thực (authenticated), kẻ tấn công có thể "bẫy" sẵn một Session ID vào trình duyệt của nạn nhân từ trước và chiếm đoạt phiên ngay sau khi họ đăng nhập. Lệnh `session.renew()` bắt buộc máy chủ phải sinh ra một Session ID hoàn toàn mới ngay thời điểm xác thực thành công.
</Callout>

## V. Xây Dựng Trang Admin Dashboard Được Bảo Vệ

Bây giờ ta xây dựng trang đích: `GET /admin/dashboard`. Trang này sẽ kiểm tra phiên làm việc:
- Nếu **chưa đăng nhập** (không tìm thấy `user_id` trong session): Lập tức chuyển hướng về `/login`.
- Nếu **đã đăng nhập**: Truy vấn tên người dùng từ cơ sở dữ liệu và hiển thị lời chào trân trọng.

```rust
//! src/routes/admin/dashboard.rs
use actix_web::http::header::ContentType;
use actix_web::{web, HttpResponse};
use sqlx::PgPool;
use uuid::Uuid;
use crate::session_state::TypedSession;
use crate::utils::{e500, see_other};

pub async fn admin_dashboard(
    session: TypedSession,
    pool: web::Data<PgPool>,
) -> Result<HttpResponse, actix_web::Error> {
    let username = if let Some(user_id) = session.get_user_id().map_err(e500)? {
        get_username(user_id, &pool).await.map_err(e500)?
    } else {
        // Chưa đăng nhập: Đẩy về trang Login!
        return Ok(see_other("/login"));
    };

    Ok(HttpResponse::Ok()
        .content_type(ContentType::html())
        .body(format!(
            r#"<!DOCTYPE html>
<html lang="en">
<head>
    <meta http-equiv="content-type" content="text/html; charset=utf-8">
    <title>Admin dashboard</title>
</head>
<body>
    <p>Welcome {}!</p>
    <p>Available actions:</p>
    <ol>
        <li><a href="/admin/password">Change password</a></li>
        <li>
            <form name="logoutForm" action="/admin/logout" method="post">
                <input type="submit" value="Logout">
            </form>
        </li>
    </ol>
</body>
</html>"#,
            username
        )))
}

async fn get_username(user_id: Uuid, pool: &PgPool) -> Result<String, anyhow::Error> {
    let row = sqlx::query!(
        r#"
        SELECT username
        FROM users
        WHERE user_id = $1
        "#,
        user_id,
    )
    .fetch_one(pool)
    .await?;
    Ok(row.username)
}
```

Kiến trúc quản lý phiên với Redis đã vận hành trơn tru: hệ thống bảo vệ toàn diện các trang quản trị nội bộ trước các truy cập trái phép.
