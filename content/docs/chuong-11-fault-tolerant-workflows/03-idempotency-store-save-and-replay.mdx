# 11.7 - 11.8 Lưu Trữ Trạng Thái: Idempotency Store & Cơ Chế Save-and-Replay

Để triển khai chiến lược **Stateful Save-and-Replay**, chúng ta cần một nơi lưu trữ bền vững (Idempotency Store) để ghi lại cặp khóa-giá trị: `(User ID, Idempotency Key) -> Phản hồi HTTP (HttpResponse)`.

---

## I. Lựa Chọn Cơ Sở Dữ Liệu: Postgres Hay Redis?

Hệ thống của chúng ta hiện đang có sẵn cả Redis lẫn PostgreSQL. Đâu là nơi thích hợp nhất để lưu Idempotency Store?

Thoạt nhìn, Redis có vẻ rất hấp dẫn vì nó hỗ trợ cơ chế tự hủy bản ghi sau một khoảng thời gian (TTL) mà không cần dọn rác thủ công.

Tuy nhiên, trong các bài toán chịu lỗi phân tán, một yêu cầu kiến trúc tối quan trọng sẽ xuất hiện: **Chúng ta cần sửa đổi trạng thái ứng dụng và cập nhật Idempotency Store bên trong CÙNG MỘT GIAO DỊCH NGUYÊN TỬ (ACID Transaction)**!
- Redis và PostgreSQL là hai hệ thống độc lập. Chúng không thể tham gia vào cùng một SQL Transaction. Nếu thao tác trên Postgres thành công nhưng ghi vào Redis thất bại (hoặc ngược lại), hệ thống sẽ rơi vào trạng thái bất nhất (inconsistent state).
- **Quyết định kiến trúc**: Chúng ta chọn **PostgreSQL**. Toàn bộ dữ liệu nghiệp vụ lẫn thông tin Idempotency sẽ nằm chung trong một cơ sở dữ liệu duy nhất, cho phép khóa dòng và rollback nguyên tử hoàn hảo.

## II. Thiết Kế Bảng `idempotency` Trong PostgreSQL

Chúng ta cần lưu trữ các thành phần cốt lõi của một phản hồi HTTP:
- `user_id`: Định danh người thực hiện thao tác.
- `idempotency_key`: Khóa bất biến do client sinh ra.
- `response_status_code`: Mã trạng thái HTTP (200, 303, 400,...) dạng số nguyên `smallint`.
- `response_headers`: Danh sách các cặp tiêu đề `(tên, giá trị)`.
- `response_body`: Phần thân phản hồi dưới dạng mảng byte nhị phân `bytea`.
- `created_at`: Thời điểm tạo để phục vụ dọn dẹp sau này.

### Xử lý mảng Tuple trong PostgreSQL bằng Composite Type

Một header HTTP có thể có nhiều giá trị khác nhau cho cùng một tên gọi. Do đó, các header được biểu diễn dưới dạng danh sách các cặp `(HeaderName, HeaderValue)`.

Vì PostgreSQL không hỗ trợ mảng của kiểu tuple trực tiếp, chúng ta định nghĩa một **Composite Type** có tên là `header_pair`:

Tạo migration mới:
```bash
sqlx migrate add create_idempotency_table
```

Nội dung file migration:

```sql
-- migrations/<timestamp>_create_idempotency_table.sql
CREATE TYPE header_pair AS (
    name TEXT,
    value BYTEA
);

CREATE TABLE idempotency (
    user_id uuid NOT NULL REFERENCES users(user_id),
    idempotency_key TEXT NOT NULL,
    response_status_code SMALLINT NOT NULL,
    response_headers header_pair[] NOT NULL,
    response_body BYTEA NOT NULL,
    created_at timestamptz NOT NULL,
    PRIMARY KEY(user_id, idempotency_key)
);
```

Chạy migration:
```bash
sqlx migrate run
```

## III. Kiểu Dữ Liệu Miền `IdempotencyKey`

Trong form gửi bản tin HTML, chúng ta bổ sung một trường input ẩn chứa `idempotency_key`:

```rust
//! src/idempotency/key.rs

#[derive(Debug)]
pub struct IdempotencyKey(String);

impl TryFrom<String> for IdempotencyKey {
    type Error = anyhow::Error;

    fn try_from(s: String) -> Result<Self, Self::Error> {
        if s.is_empty() {
            anyhow::bail!("The idempotency key cannot be empty");
        }
        let max_length = 50;
        if s.len() >= max_length {
            anyhow::bail!("The idempotency key must be shorter than {max_length} characters");
        }
        Ok(Self(s))
    }
}

impl AsRef<str> for IdempotencyKey {
    fn as_ref(&self) -> &str {
        &self.0
    }
}
```

Kiểu `IdempotencyKey` bảo đảm rằng mọi khóa đi vào hệ thống đều không được rỗng và có độ dài tối đa 50 ký tự (đủ cho định dạng UUID v4 chuẩn).

## IV. Cơ Chế Lưu Trữ Và Tái Hiện Phản Hồi (Save And Replay)

Module `src/idempotency/persistence.rs` phụ trách việc lưu trữ và khôi phục `HttpResponse`:

### 1. Truy xuất phản hồi đã lưu (`get_saved_response`)

Khi có request gửi đến, hàm này kiểm tra xem trong bảng `idempotency` đã có kết quả tương ứng với `(user_id, idempotency_key)` hay chưa:

```rust
//! src/idempotency/persistence.rs
use actix_web::HttpResponse;
use sqlx::PgPool;
use uuid::Uuid;
use crate::idempotency::IdempotencyKey;

pub async fn get_saved_response(
    pool: &PgPool,
    idempotency_key: &IdempotencyKey,
    user_id: Uuid,
) -> Result<Option<HttpResponse>, anyhow::Error> {
    let saved_response = sqlx::query!(
        r#"
        SELECT 
            response_status_code,
            response_headers as "response_headers: Vec<HeaderPairRecord>",
            response_body
        FROM idempotency
        WHERE 
            user_id = $1 AND
            idempotency_key = $2
        "#,
        user_id,
        idempotency_key.as_ref()
    )
    .fetch_optional(pool)
    .await?;

    if let Some(r) = saved_response {
        let status_code = StatusCode::from_u16(r.response_status_code as u16)?;
        let mut response = HttpResponse::build(status_code);
        for HeaderPairRecord { name, value } in r.response_headers {
            response.append_header((name, value));
        }
        Ok(Some(response.body(r.response_body)))
    } else {
        Ok(None)
    }
}
```

### 2. Lưu phản hồi mới (`save_response`)

Sau khi request được thực thi thành công, chúng ta trích xuất `status_code`, `headers` và `body` từ `HttpResponse` rồi ghi vào PostgreSQL:

```rust
//! src/idempotency/persistence.rs

pub async fn save_response(
    pool: &PgPool,
    idempotency_key: &IdempotencyKey,
    user_id: Uuid,
    http_response: HttpResponse,
) -> Result<HttpResponse, anyhow::Error> {
    let (response_head, body) = http_response.into_parts();
    // Đọc toàn bộ body stream thành mảng byte
    let body = actix_web::body::to_bytes(body).await.map_err(|e| anyhow::anyhow!("{}", e))?;
    let status_code = response_head.status().as_u16() as i16;
    
    let headers = {
        let mut h = Vec::with_capacity(response_head.headers().len());
        for (name, value) in response_head.headers().iter() {
            let name = name.as_str().to_owned();
            let value = value.as_bytes().to_owned();
            h.push(HeaderPairRecord { name, value });
        }
        h
    };

    sqlx::query!(
        r#"
        INSERT INTO idempotency (
            user_id,
            idempotency_key,
            response_status_code,
            response_headers,
            response_body,
            created_at
        )
        VALUES ($1, $2, $3, $4, $5, now())
        "#,
        user_id,
        idempotency_key.as_ref(),
        status_code,
        headers as Vec<HeaderPairRecord>,
        body.as_ref()
    )
    .execute(pool)
    .await?;

    // Tái tạo lại HttpResponse ban đầu để trả về cho client
    let http_response = response_head.set_body(body);
    Ok(http_response)
}
```

### 3. Tích hợp vào Request Handler

Bây giờ chúng ta lắp ghép cơ chế Save-and-Replay vào `publish_newsletter`:

```rust
//! src/routes/admin/newsletter/post.rs

pub async fn publish_newsletter(
    form: web::Form<FormData>,
    pool: web::Data<PgPool>,
    email_client: web::Data<EmailClient>,
    user_id: web::ReqData<UserId>,
) -> Result<HttpResponse, actix_web::Error> {
    let user_id = user_id.into_inner();
    let idempotency_key: IdempotencyKey = form.0.idempotency_key.try_into().map_err(e400)?;

    // BƯỚC 1: Kiểm tra xem đã có phản hồi lưu sẵn chưa
    if let Some(saved_response) = get_saved_response(&pool, &idempotency_key, *user_id).await.map_err(e500)? {
        FlashMessage::info("The newsletter issue has been published!").send();
        return Ok(saved_response);
    }

    // BƯỚC 2: Nếu chưa có, thực hiện gửi email bình thường
    // [...] (vòng lặp gửi email)

    // BƯỚC 3: Lưu lại phản hồi trước khi trả về
    let response = see_other("/admin/newsletters");
    let response = save_response(&pool, &idempotency_key, *user_id, response).await.map_err(e500)?;
    FlashMessage::info("The newsletter issue has been published!").send();
    Ok(response)
}
```

Chạy lại bài kiểm thử ở bài trước, kịch bản thử lại tuần tự (`newsletter_creation_is_idempotent`) đã chính thức chuyển sang màu xanh (`passed`)!
